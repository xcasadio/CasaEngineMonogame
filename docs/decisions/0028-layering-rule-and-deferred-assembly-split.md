# ADR-0028: Core-Engine-Framework layering rule and deferred assembly split

- **Status**: Accepted
- **Date**: 2026-09-06 (backfill)
- **Source**: `ai-agent/audits/CasaEngine_layering_project_split_evaluation.md:7-15,26-31,35-53,55-59`; `ai-agent/audits/structure-analyze-tasks.md:33,37-39,380-382`; `ai-agent/audits/CasaEngine_folder_hierarchy_audit_report.md:298-299,304,504`

## Context

`HIER-011` asked whether `CasaEngine` should now be split into `CasaEngine.Core`, `CasaEngine.Engine` and `CasaEngine.Runtime` projects (`CasaEngine_layering_project_split_evaluation.md:7-11`). At the time of the evaluation, the physical folder hierarchy already reflected the intended layers better, the `Engine -> Framework` dependency leak found in `Primitive2D` had been removed, and `Core`/`Engine`/the high-level runtime were more readable — but several things still blocked an immediate clean split: many historical namespaces were kept for compatibility, several layers were still grouped in a single MSBuild project, some categories had been reorganized physically without a full namespace rename, and a real split would need a dedicated pass on references, `InternalsVisibleTo`, tests and editor projects (`CasaEngine_layering_project_split_evaluation.md:19-31`).

The layer dependency rule is stated in `structure-analyze-tasks.md` as: "La seule règle de couche à contrôler est : **Core ne doit pas référencer Engine ni Framework**, et **Engine ne doit pas référencer Framework**." (`structure-analyze-tasks.md:33`). The same document restates it in English a few lines below: "The expected dependency rule: **Core** has zero inward dependencies, **Engine** depends only on Core, **Framework** depends on Engine + Core. No reverse dependencies allowed." (`structure-analyze-tasks.md:37-39`). The two phrasings differ slightly (the first only forbids referencing upward; the second additionally states Engine depends on Core and Framework depends on Engine+Core), both are reproduced here verbatim. `CasaEngine_folder_hierarchy_audit_report.md:298-299` confirms the same rule as an observed fact: "`Core` ne dépend pas de `Engine` ni de `Framework`." and "`Framework` dépend logiquement de `Core` et `Engine`."

Separately, `structure-analyze-tasks.md:380-382` records that `IGameplayProxy` in `Scripting/` had a residual cycle with `Entities/`, fixed by changing `IGameplayProxy.Clone()` to return `IGameplayProxy` instead of the concrete `GameplayProxy` type, breaking the `Entities ↔ Scripting` cycle.

## Decision

- The layer dependency rule to enforce across the codebase is: Core must not reference Engine or Framework, and Engine must not reference Framework (Core has zero inward dependencies; Engine depends only on Core; Framework depends on Engine and Core) (source: `structure-analyze-tasks.md:33,37-39`; confirmed observation: `CasaEngine_folder_hierarchy_audit_report.md:298-299`). References to MonoGame (`Microsoft.Xna.Framework`) from `Core/` and `Engine/` are normal and are not a layering violation (source: `structure-analyze-tasks.md:33` preamble).
- Splitting `CasaEngine` into separate `CasaEngine.Core`, `CasaEngine.Engine` and `CasaEngine.Runtime` assemblies is accepted in principle but deferred: "Oui à terme, mais pas immédiatement dans la même phase que la réorganisation physique des dossiers." (source: `CasaEngine_layering_project_split_evaluation.md:13-15`). The split is further gated on semantic cleanup and fixing upward dependencies first: "envisager un découpage par assembly (`CasaEngine.Core`, `CasaEngine.Engine`, `CasaEngine.Runtime`) seulement après nettoyage sémantique et correction des dépendances montantes" (source: `CasaEngine_folder_hierarchy_audit_report.md:504`).
- `IGameplayProxy.Clone()` returns the `IGameplayProxy` interface rather than the concrete `GameplayProxy` type, to break the `Entities ↔ Scripting` dependency cycle (source: `structure-analyze-tasks.md:380-382`).

## Consequences

- The split is phased and not started as a project restructuring: Phase A — stabilization after the folder refactor (validate builds/tests/tools, decide which historical namespaces must really be migrated); Phase B — pre-split (remove remaining cross-layer dependencies, reduce implicit global access, verify editor/runtime usage per candidate folder); Phase C — split by projects (create `CasaEngine.Core`, `CasaEngine.Engine`, `CasaEngine.Runtime`, migrate references progressively, optionally keep a temporary aggregator project) (source: `CasaEngine_layering_project_split_evaluation.md:35-53`). `HIER-011` itself was considered done "au sens demandé" once the opportunity was studied and the conclusion reached, without requiring the split to happen immediately (source: `CasaEngine_layering_project_split_evaluation.md:55-59`).
- Implementation status observed: the engine still ships as a single `CasaEngine.csproj` (verified: `fd -e csproj` lists one root `CasaEngine/CasaEngine.csproj`, with separate satellite projects such as `CasaEngine.Editor`, `CasaEngine.EditorServices`, `CasaEngine.Compiler`, `CasaEngine.Demos`, `CasaEngine.Tests`, `CasaEngine.Launcher`, `CasaEngine.Shaders`, `CasaEngine.DotNetCompiler`, `CasaEngine.AposShapes` — none named `CasaEngine.Core`/`.Engine`/`.Runtime`). Phases A–C have not been executed; the split remains deferred.
- `IGameplayProxy.Clone()` returning `IGameplayProxy` is implemented and verified in code: `public interface IGameplayProxy { … IGameplayProxy Clone(); }` (`CasaEngine/Framework/Scripting/IGameplayProxy.cs:7,18`).
- A follow-up improvement noted at the same source but not decided here: moving `IGameplayProxy` from `Scripting/` into `Entities/` so `Scripting.GameplayProxy` implements it and `Entities.Entity` uses it without any reverse dependency (source: `structure-analyze-tasks.md:401`) — left open, not part of this decision.
